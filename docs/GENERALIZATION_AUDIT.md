# 泛化能力审计（独立 holdout）

> **日期**：2026-09-26
> **动机**：项目此前所有「通过率」数字都取自同一份、且被反复调参过的评测集，**不能作为泛化证据**。
> 本文用独立撰写的 holdout 样本做一次诚实的泛化测量，并记录由此暴露的根因与修复。
> **判据来源**：`docs/GRADING_STANDARD.md`（唯一分级标准）。本审计只引用它，不另立标准。

| 旧结论 | 失效原因 |
|---|---|
| 「官方评测 32/32，通过率 1.0」 | 该 32 例在 2026-08~09 两轮修复中被**逐条对照调参**，属训练集而非测试集 |

| 「多智能体 24/24」 | 测的是编排链路与降级，不涉及研判准确率，不能当作泛化证据 |

**结论**：在本次审计之前，本项目**没有任何**可信的泛化数字。

## 2. 方法

### 2.1 三份样本集，用途严格区分

| 集 | 样本数 | 用途 | 是否可作泛化证据 |
|---|---|---|---|
| **v1**（H-01~H-13） | 13 | 首次测量 → 暴露 6 类根因 → **转为开发集** | ❌ |
| **v2**（V-01~V-14） | 14 | 验证修复是否泛化 → 又暴露 2 类边界 → **转为开发集** | ❌ |
| **v3**（W-01~W-15） | 15 | **冻结**：只跑一次，无论结果好坏直接计入，**不据其回调任何规则** | ✅ |

所有期望值**先于运行**确定，依据 `GRADING_STANDARD.md`，不针对模型输出反向调参。

### 2.2 样本覆盖

误报降噪（FP）/ 攻击识别（ATK）/ 分级边界（EDGE）三类，含以下刻意设计的边界：

- 否定语境陷阱（`no admin$ access`、`no mimikatz executed`、`not in admin group baseline`）
- 交互 vs 无交互（文档触发执行 = high / 远程下发执行 = critical）
- 投递 vs 执行（邮件拦截 = 投递 / 文档已 spawn 解释器 = 执行）
- 审计路径登录（`low` 但**不判误报**）与例行只读枚举（判误报）的区分
- 有变更单掩护的数据外传（high）与无掩护（critical）

## 4. holdout 暴露的 6 类根因与修复

全部修复都**从分级标准推导**，而非针对样本追加关键词。

| # | 根因 | 临床表现 | 修复 |
|---|---|---|---|
| 1 | **否定语境盲区** | `no admin$ access` 被当作管理共享访问；`not in admin group baseline` 被当作误报线索 → 正常运维升为 high（误报失效） | 新增 `security_agent/textmatch.py`：否定作用域=**子句**，三处（规则引擎/预筛/误报检查）共用一份实现 |
| 2 | **反弹 shell 覆盖缺失** | `bash -i >& /dev/tcp/…` 被兜底为「通用异常行为 / medium」（漏判） | 依 ATT&CK T1059.004/T1071 纳入「恶意脚本执行」特征 |
| 3 | **弱减分越权** | 一条误报线索把已确认的横向移动从 62 分压到 59 → high 掉成 medium | 依标准第 3 节设攻击类型分数下限（= medium 起点）；受审计合法运维登录除外 |
| 4 | **LOLBin 误列脚本特征** | `rundll32.exe` 出现在「恶意脚本执行」特征表里，C2 信标事件被误吸 | 移出该特征表（rundll32 正常软件亦大量调用） |
| 5 | **投递规则压过执行规则** | 预筛按「证据分=权重×命中词数」取主规则，宏投递规则凭命中词多压过脚本执行规则 | 给规则加 `stage`（execution/delivery/intel），依标准 2.1①**以已发生执行者为准**；情报命中降为上下文，不参与阶段竞争 |
| 6 | **无交互远程执行未升档** | 远程服务下发、无用户交互的编码命令只记 high | 依标准判据③ 落地「无用户交互的远程/自动执行 → critical」 |

修复过程中另发现并修正 2 处**由修复自身引入**的副作用（EVENT-009 被分数下限误抬、EVENT-010 被情报规则抢分类），均已在评测集上回归确认。

## 5. 附带发现：评测装置缺陷（三条污染通路）

这三条都不是模型缺陷，都会**让评测结果失去意义**。它们也解释了为什么「同样的代码、跑两次结果不同」。

> **共性**：三条通路的根因是同一个架构假设——**事件彼此隔离**。评测集的每条用例都假设
> 「只按本事件的证据判决」，但检索层是按**主机 / 账号 / 记忆**这些**跨事件共享的键**去取上下文的。
> 只要设备/账号在不同事件间复用，上下文就会串台。

### 5.1 日志跨事件污染

**现象**：真 LLM 在 EVENT-013（域控运维例行共享目录核查，期望「误报」）上判 `critical / 恶意脚本执行`，且**推理链正确**——它引用的是「DC-01 上 10:00 有 WinRM 远程 `Invoke-Expression`、08:00 有安全日志清除」。

**根因**：`data/logs.json` 按**主机**静态写死，且 `LogLookupTool` 只按「主机 **或** 账号」匹配。DC-01 同时被 EVENT-001（域控 PowerShell 攻击）与 EVENT-013 使用，于是 **EVENT-013 被灌进了 EVENT-001 的攻击证据**。

**性质判定**：**评测装置缺陷，不是模型缺陷**——模型的判断在给定证据下是正确的，是标注假设了「事件彼此隔离」而装置未保证隔离。

**已修复（两轮，第二轮才是真修复）**：

- 第一轮：`LogRecord` 增加 `event_id` 归属字段，`logs.json` 14 条记录补齐归属，`find_logs()` 改为「事件作用域优先，作用域为空时回落主机/账号匹配」。
  → **无效**。EVENT-013 自身没有日志，作用域命中为空，**恰好掉进回落分支**，污染原样复现。
- 第二轮（正确修法）：改为**按数据集是否已标注判定**——数据集一旦存在 `event_id` 标注，则全局启用**严格作用域**，本事件无日志即返回空，**不得回落**。只有在数据集完全无标注（旧格式）时才回落主机/账号匹配。

> **教训（已工程化的判据）**：`if scoped: return scoped` + `return fallback` 这种「空则回落」写法，
> 在数据隔离场景里等价于**没修**——需要隔离的对象恰恰是**没有自有数据**的那些。
> 判定条件应取自**数据集格式**（全局属性），而不是**单次查询结果**（局部属性）。

**验证**：真 LLM 下 EVENT-013 恢复 `low / 误报`；且模型推理中出现「关联日志与历史告警均为空」，
并与镜像样本 EVENT-004（同为主机 + `net.exe` + 共享，期望 `high / 横向移动前置`）**正确区分**——
同一工具、同一模型，仅凭「是否真有 `admin$` 远程访问证据」分开，说明隔离修复恢复了样本的判别力。

> 注：该问题 2026-09-01 已在 `QUALITY_IMPROVEMENT.md` 1.1 记录，但当时**只修了预筛器语料**，
> 喂给 LLM 的日志工具一直没修 —— 本次补完（含上一轮不彻底的回落写法）。

### 5.2 误报记忆自我污染（评测不幂等）—— 更严重

**现象**：`data/triage_history.jsonl` 被历次评测写满 200 条（上限即 200），其中 `EVENT-001..012`、`EVENT-031..038` **各重复 5–6 次**——全部是评测自身的裁决残留。

**根因链**：
1. `SecurityAgent._triage()` 每次研判都会把裁决写入误报记忆（受 `record_history` 开关控制）；
2. `EvaluationService.evaluate()` **从未把这个开关关掉**——`orchestrator.py` 里写着注释「评测时会临时关闭，避免污染记忆」，
   但该开关实际只被 Web 端使用（`web/server.py`），评测路径从未关闭；
3. 下一轮评测时，`MemoryStore.search()` 按**同主机**匹配取回历史裁决，并注入 LLM 提示词（「历史研判记忆」章节）；
4. 于是 **EVENT-013（主机 DC-01）取回了 EVENT-001（同主机）的 `恶意脚本执行 / critical` 裁决**并照此判决。

**后果**：评测**不幂等**——同代码跑两次结果不同；样本数越多、跑得越多，污染越重。

**已修复**：
- `EvaluationService.evaluate()` 在评测期间强制 `app.record_history = False`（`finally` 恢复）；
- `scripts/_holdout_eval.py` 同样关闭；
- 已污染的 `triage_history.jsonl`（200 条评测残留）备份至 `.workbuddy/backup/triage_history.jsonl.bak-20260926` 后清空。
- 验证：连跑两轮评测均 **38/38**，记忆文件保持 0 字节（幂等）。

**影响面**：污染按**主机**扩散，凡主机被多条用例复用者均受影响。修复前 38 例中明确可归因的是 EVENT-013。

**二次收口（同日补）——「只关写」仍不够，读也须隔离**：
- 只关写时，磁盘上任何**存量**记忆（生产运行残留、早期未关写时的遗留）都会被
  `MemoryStore.search` 取回注入提示词——同一份代码在不同机器、不同时刻仍会跑出不同数字。
- 实验验证：向记忆植入 3 条针对 DC-01 的诱导记录（「net.exe 横向移动 / critical」），
  确认可被 EVENT-013 检索到后，评测结果**不受影响**（38/38），生产记忆零写入。
- 最终实现：`evaluate()` 把 `app.memory` 指向 `tempfile` 下的临时空库（`finally` 恢复原引用），
  写隔离与读隔离**同处一个实现**，`evaluate_modes()` 三模式均经由它，自动覆盖。
- **工程教训**：修复落盘后，此前用旧代码快照跑出的 LLM 结果一律作废重测——后台评测进程
  在启动时加载代码，其运行结果不代表磁盘上的当前修复。隔离实验三步法（清空 → 对照组写入
  应生效 → 评测路径应零写入）可整体复用。

### 5.3 历史告警的异主机注入（来源未标注）—— 弱通路，已识别

**现象**：`data/history_alerts.json` 的 `HIST-008` 为 `DMZ-WEB-003 / www-data / 疑似 C2 信标 / high`。
而 `www-data` 是**通用 Web 服务账号**，EVENT-006、EVENT-022、EVENT-033（分别为 WEB-01、WEB-02、WEB-PORTAL-01）
都以该账号运行。`HistoryAlertLookupTool` 按「主机 **或** 账号」匹配 → 这三条事件都会被注入 `HIST-008`。

**为什么是缺陷**：真 SOC 中「同账号在别的机器有告警」是**弱线索**，可用；
但此处 `www-data` 属**通用账号名**，跨主机同名不构成有意义的关联，注入的是巧合而非情报。
更关键的是——**工具详情行只输出 `时间 标题 | 风险 | 结论`，没有主机名**，
模型无从知道这条「历史告警」来自另一台机器，只能当作本机历史照单采信。

**当前可观测影响：无**。三例 Web 事件本身即为 `critical/high`，注入的 `high` 不改变结论；
规则路径与真 LLM 路径该三例均通过。因此**不列为已造成失真的缺陷，只列为已识别风险**。

**拟定修法（待应用）**：`find_history_alerts` 保留「主机或账号」召回，但在工具输出中
**显式标注来源主机**，并对异主机记录加标记（如 `[异主机 DMZ-WEB-003]`），
让模型按线索强弱自行赋权，而不是把巧合当本机历史。

### 5.4 判据沉淀：跨事件共享键该怎么分类

排查完三条通路后，对「哪些共享键需要隔离」形成了一个**可复用的判据**——
判据不是「这个键是否被多条事件共享」，而是**这条数据是「事件私有的观测」还是「全局共有的知识」**：

| 共享键 | 数据性质 | 正确处置 |
|---|---|---|
| 主机 → 日志 | **事件私有观测**（该事件的现场取证证据） | **必须**事件作用域严格隔离（5.1） |
| 主机 → 研判记忆 | **事件私有结论**（上一次对同一证据的裁决） | 评测期**禁止写入**（5.2） |
| 账号 → 历史告警 | **弱关联线索**（通用账号同名属巧合） | 可召回，但**必须标注来源**供模型赋权（5.3） |
| IOC → 威胁情报 | **全局共有知识**（同一 IOC 的结论本就唯一） | **不需隔离**——隔离反而错误 |
| 主机 → 资产画像 | **全局共有知识**（主机属性与事件无关） | 不需隔离 |

**反面教训**：若把「共享 IOC 情报」也按事件隔离，同一恶意域名在不同事件里会得到不同情报结论，
反而制造新的不一致。**隔离的对象是「事件产生的数据」，不是「被事件引用的数据」。**

**现状核对**：本轮已逐键核对 `alerts.json` 的 5 类共享键（`destination_ip` / `destination_domain` /
`source_ip` / `user` / `process`）与 `intel.json` 的 9 条指标复用情况。
除 `user`（→5.3）与 `destination_domain: malware-c2.example.com`（2 例，属**全局 IOC 事实**，按上表**不应隔离**）外，无其他跨事件泄漏面。

## 6. 诚实限制（必须随结果一起引用）

1. **v1/v2 已降级为开发集**：本文表中 v1/v2 的「修复后」数字**不是**泛化证据；只有 v3 可引用。
2. **v3 由本项目作者撰写**，与实现共享同一套词汇习惯，**不等于第三方基准**。它比「自测自评」强，但不能替代外部数据集（对照：CyberSOCEval、ExCyTIn-Bench）。
3. **样本量小**：v3 仅 15 例，单例权重 6.7%，不适合做统计显著性结论。
4. **v3 冻结时点为 2026-09-26**。此后任何规则改动都应重开 v4，不得再引用 v3。
5. 领域覆盖已从 1 个垂类扩到 2 个（应急响应 32 例 + Web 漏洞利用 6 例），仍缺**漏洞挖掘 / 逆向分析**两类。
